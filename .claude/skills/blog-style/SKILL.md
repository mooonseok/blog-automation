# blog-style

이 파일은 계속 바뀐다. 규칙이 충돌하면 **사용자 피드백 > 학습된 규칙 > 기본 규칙** 순서로 따른다.
기준 예시는 `examples/pstack-example.md`다. 규칙보다 예시를 먼저 본다. 출처는 `references.md`, 변경 이력은 `changelog.md`.

## 0. 이 블로그 글이 하는 일

영상을 **요약하지 않고 재창조**한다. 영상을 안 본 사람이 (그리고 블로그 주인 자신이) 이 글만 읽고 핵심을 이해하고 기억하게 만든다.

- **숏폼처럼 슥슥 읽힌다**: 1~2문장 문단, 문단마다 빈 줄, 화면마다 시선이 쉬는 부품
- **공부가 된다**: 질문으로 궁금하게 만들고, 답하고, 예시로 붙잡고, 한 줄로 정리한다
- **주인공을 확실히 설명한다**: 영상이 다루는 도구·개념(예: pstack)이 무엇이고, 무엇으로 이루어졌고, 어떻게 동작하는지는 반드시 설명한다. 이 설명을 빼고 일반론(예: "검증 습관")으로 바꾸면 실패다
- **곁가지는 버린다**: 버전 번호, 내부 설정값, 곁가지 일화처럼 주인공 이해에 필요 없는 것만 버린다. 주인공 설명은 버리는 대상이 아니다

## 1. 블로그 정보

- 주소: https://moonesok.tistory.com, 기본 카테고리 `AI`
- 발행: `sh copy-post`가 post.md를 HTML로 바꿔 복사한다. 티스토리 **HTML 모드**에 붙여넣는다.
- 본문에 `#` 제목을 넣지 않는다 (제목은 티스토리 제목 칸).

## 2. 말투

- **평서체 `~다`**. 해요체(`~요`)를 쓰지 않는다. 단, 인용 부품 안의 발언과 따옴표 안 대사는 그대로 둔다.
- 독자에게 말을 건다. 질문을 던지고 (`~일까?`), 독자가 겪어 봤을 장면을 쓴다.
- 보고서체를 쓰지 않는다. `화자는 ~라고 본다`, `영상에서는 ~를 강조한다`를 반복하지 않는다. 발행본에 자동 출처 목록을 붙이지 않고, 본문은 내용 자체를 주어로 쓴다. 원재료·근거는 analysis.md와 meta.json에 보관한다. 직접 인용을 쓴다면 화자를 명시하고, 실제 경험인 것처럼 꾸미지 않는다.
- 문장 끝을 다양하게: `~다`만 이어지면 체언 종결이나 짧은 단문을 섞는다 (`결론은 간단하다. 직접 돌려 본다.`).

## 3. 글 구조 (고정 템플릿)

| 순서 | 블록 | 분량·규칙 |
|---|---|---|
| 1 | **도입 훅** | 1~2문장 문단 2~3개. 독자가 겪어 봤을 장면이나 질문으로 시작. 마지막 문단에서 이 글의 주인공을 한 줄로 소개 |
| 2 | **한눈에 보기** `:::summary` | 핵심 한 문장 + ✓ 3개 + 이 글에서 답할 질문 3개 |
| 3 | **Q1: 주인공 설명 (필수)** `## Q1. <주인공>은 무엇이고 어떻게 동작할까?` | 아래 "Q1 필수 요소"를 모두 담는다. 다른 섹션보다 길어도 된다 |
| 3-2 | **Q2~Q3** `## Q2. 질문?` | 주인공의 핵심 기능이나 쓰는 법, 한계를 다룬다. 섹션마다 아래 "네 박자" |
| 4 | **마무리** | 주제에 맞는 결론 1~2문장으로 자연스럽게 끝낸다. 행동 과제나 출처 목록을 덧붙이지 않는다. 필요하면 `<!-- 내 생각: 직접 한두 줄 추가 -->` |

- 전체 분량: **본문 1,800~3,500자** (부품·표 포함, 마크다운 기호 제외). 넘으면 Q2·Q3의 덜 중요한 문단부터 자른다. Q1의 필수 요소는 자르지 않는다.
- 소제목은 Q1~Q3 세 개가 기본. 내용상 꼭 필요할 때만 Q4. `###`는 쓰지 않는다.

### Q1 필수 요소 (주인공 설명)

영상을 보지 않은 사람이 Q1만 읽고 "아, 그게 그거구나" 하고 남에게 설명할 수 있어야 한다.

1. **한 줄 정의** (굵게): 무엇인지 한 문장. `**pstack은 숙련 개발자의 작업 순서를 AI에게 그대로 따르게 하는 Claude Code·Cursor용 스킬 묶음이다.**`
2. **왜 생겼나**: 어떤 문제를 풀려고 나왔는지 1~2문단. 독자가 겪는 장면으로.
3. **무엇으로 이루어졌나**: 핵심 구성 요소 2~4개를 각각 한 줄로 (용어 상자, 표, 단계 중 하나). 개수 같은 세부 숫자보다 역할을 설명한다.
4. **어떻게 동작하나**: 사용자가 요청한 순간부터 결과가 나오기까지의 흐름을 `:::steps`로 3~5단계. 구체적인 예시 하나(예: "버그를 고쳐 줘"라고 했을 때)를 따라간다.
5. **비슷한 것과의 차이**: 독자가 헷갈릴 만한 대상이 있으면 표로 비교 (없으면 생략).
6. **한 줄 정리**: `:::takeaway`

### 섹션 하나의 네 박자 (Q2~Q3)

1. **질문 훅** = 소제목. `## Q2. ~할까?` 독자가 실제로 궁금해할 질문으로 쓴다.
2. **한 줄 답** = 소제목 바로 아래 첫 문단, 전체를 굵게. `**역할을 흉내 내는 게 아니라, 일하는 순서를 강제한다.**`
3. **설명 + 예시** = 1~2문장 문단 2~4개. 추상적인 말 바로 뒤에 장면, 숫자, 비유를 붙인다. 필요하면 부품(표, 단계, 용어, 팁, 이미지)을 하나 둔다.
4. **한 줄 정리** = `:::takeaway`. 섹션의 결론을 외우기 쉬운 한 문장으로. 핵심 구절은 `==형광펜==`.

## 4. 문단과 문장

- **문단은 1~2문장. 최대 3문장.** 문단 사이는 반드시 빈 줄 하나 (변환기가 티스토리 빈 문단으로 바꾼다).
- 한 문장에 정보 하나. 50~60자 안팎. 쉼표로 절을 셋 이상 잇지 않는다.
- 같은 형태의 문단(설명만 3개 연속)이 이어지면 사이에 부품이나 짧은 질문 문장을 넣어 리듬을 바꾼다.
- 굵은 글씨는 문단당 최대 1개. 한 줄 답과 체크 항목의 핵심어에만.
- 구체적으로 쓴다. 수치가 있으면 수치, 장면이 있으면 장면. 근거 없는 `~할 수 있다`는 단정으로.

## 5. 부품 (변환기가 디자인을 입힌다)

`>` 인용 블록과 `---` 구분선은 쓰지 않는다. 상자는 모두 아래 부품으로 만든다.

| 부품 | 문법 | 언제 | 글당 개수 |
|---|---|---|---|
| 한눈에 보기 | `:::summary` 첫 줄=핵심, `- `=체크, `? `=질문 | 도입 바로 뒤 | 1 (필수) |
| 한 줄 정리 | `:::takeaway` 한 문장, `==구절==` 형광펜 | 각 Q 섹션 끝 | 섹션당 1 |
| 용어 | `:::term` `**용어**: 한 줄 뜻` | 처음 나오는 전문용어 | 0~2 |
| 팁 | `:::tip` | 바로 써먹을 요령 | 0~1 |
| 주의 | `:::warn` | 함정, 쓰지 말아야 할 때 | 0~1 |
| 인용 | `:::quote 화자` 한 문장 | 기억할 만한 발언 (확인된 것만) | 0~1 |
| 단계 | `:::steps` 줄마다 `제목 \| 설명` | 순서가 있는 3~5단계 | 0~2 |
| 체크리스트 | `:::checklist` 줄마다 `- 항목` | 본문 설명에 꼭 필요한 점검 기준 | 0~1 (선택). 마무리 행동 과제로 붙이지 않는다 |
| 표 | 마크다운 표 | 2~3개를 같은 기준으로 비교 | 0~1 |
| 이미지 | `[[이미지 N]]` | 6장 참고 | 0~2 |

- 부품 앞에는 무엇을 보여 주는지 한 문장을 둔다 (`버그를 고칠 때의 순서로 보면 이렇다.`). 한눈에 보기와 한 줄 정리는 예외.
- 표는 열 3개 이하, 셀은 한 구절. 첫 열은 비교 항목.

## 6. 이미지

주제를 드러내는 대표 일러스트 1장과, 필요하면 복잡한 관계를 설명하는 도식 1장을 계획할 수 있다. 글당 최대 2개. 장식용으로 억지로 추가하지 않고, 이미지 없이도 개념은 이해되게 쓴다. 일러스트는 이미지 생성용 프롬프트를, 정확한 글자·화살표가 필요한 도식은 SVG/PNG 제작 명세를 적는다. 자동 생성·업로드는 아직 구현되지 않았으므로 파일이나 URL이 있는 것처럼 쓰지 않는다.

- 본문에 `[[이미지 N]]`을 넣고, 같은 폴더 `images.md`에 아래 형식으로 적는다.
  ```markdown
  ## 이미지 1: 하네스 5층 구조
  - 위치: Q3 섹션, "아래층으로 갈수록 강해지는 구조다" 문단 다음
  - 목적: 아래층일수록 규칙이 강하게 지켜진다는 것을 한눈에
  - 비율: 16:9 (1200×675)
  - 대체 텍스트: 코드베이스부터 스타일 가이드까지 다섯 층으로 쌓인 구조
  - 프롬프트 (영문): ...
  - 캡션: ...
  ```
- **공통 이미지 스타일** (모든 프롬프트 끝에 붙인다): `Flat vector illustration, clean white background, blue color palette (#3d62ce accents), soft shadows, modern tech blog style, no text.`
- 이미지 생성 도구는 한글을 깨뜨리므로 그림 안에 글자를 넣지 않는다. 설명은 캡션으로.

## 7. 링크

- **영상 링크, 타임스탬프 링크를 넣지 않는다.**
- 사람·저장소·도구는 **직접 열어 확인한 주소만** 이름에 링크한다. `@핸들`, 맨 URL을 노출하지 않는다.
- 링크 텍스트는 2~4단어, 같은 대상은 처음 한 번만.

## 8. 쓰지 않을 것

- **S0 (절대 금지, 발견 즉시 문장째 삭제)**: 글을 만든 과정이나 검증 여부에 대한 말.
  - 예: `현재 배포본의 동작은 별도로 확인하지 않았다`, `자막 기준으로 정리했다`, `영상에서 설명한 내용을 정리했으며`, `이 글은 ~를 바탕으로 작성됐다`
  - 확인되지 않은 사실은 쓰지 않거나 `<!-- 확인 필요 -->` 주석으로만 표시한다.
- 발행본에 `## 출처`, `## 참고자료` 같은 자동 출처 목록과 `## 오늘부터 바로 써먹기`, `## 오늘부터 해볼 것` 같은 마무리 행동 과제는 넣지 않는다. 근거는 내부 파일에 남긴다. 주제를 설명하는 본문 절차·비교·점검 기준은 허용한다.
- **S1 (즉시 수정)**: 예고 (`이번 글에서는 ~를 알아보겠다`, `결론부터 말하면`), 판에 박힌 마무리, `~라고 할 수 있다`, em dash(—), 해요체
- **S2 (반복되면 수정)**: 번역투 (`~에 대해`, `~를 통해`, `~에 있어서`), `~하는 것이다`, `~하게 되었다`, `진행/수행/실시`, 피동 남발
- **S3 (겹치면 수정)**: 습관적 3개 나열, 같은 시작어 반복, `중요하다/핵심적/효과적` 같은 뭉뚱그린 평가어, 강조 부사
- **의미 없는 정보**: 버전 번호, 구성 개수, 내부 설정값처럼 "그래서 독자에게 뭐가 좋은가?"에 답하지 못하는 것은 본문에 넣지 않는다 (`analysis.md`에만 남긴다).

## 8-1. AI 티 없애기 (im-not-ai 차용)

[im-not-ai](https://github.com/epoko77-ai/im-not-ai)(humanize-korean)의 한국어 AI 티 규칙을 **쓰는 단계에서부터** 적용한다. 다 쓴 뒤 따로 윤문 단계를 돌리지 않는다 (부품 문법이 깨지고 문장이 길어지기 때문).

- **규칙집**: `~/.agents/skills/humanize-korean/references/quick-rules.md` (전역 설치돼 있으면 writer·editor가 처음부터 끝까지 읽는다. 없으면 아래 요약만 따른다)
- **우리 블로그에 맞게 바꾼 점**
  - **E-1(100자 넘는 장문 섞기)은 적용하지 않는다.** 숏폼 규칙(문장 50~60자, 문단 1~2문장)이 우선이다.
  - C-2(불릿 과다)·C-5(이모지)·J-3(대시)는 **본문 글에만** 적용한다. 부품(:::steps, :::checklist)과 변환기가 넣는 📌·✓·— 는 예외.
  - D-3(열거 도입 "다음과 같다")을 피한다. 부품 앞 한 문장은 무엇을 보여 주는지 구체적으로 쓴다 (`버그를 고칠 때의 순서로 보면 이렇다.`).
  - 사실·수치·고유명사·인용은 바꾸지 않는다. "~해야 한다"를 "~한다"로 바꾸지 않는다 (서법 보존).
- **가장 자주 걸리는 신호** (`tools/lint_post.py`가 검사한다)

| 신호 | 고치는 법 | 검사 |
|---|---|---|
| C-11 연결어미 뒤 쉼표 (`켜고,` `재현하고,` `줄이려고,`) | 쉼표를 지운다. 새로 만들지 않는다 | 오류 |
| E-2 `~ㄴ다/~는다` 종결 4문장+ 연속 | 체언 종결, `~이다`, 짧은 질문으로 리듬을 깬다 | 경고 |
| I-4 `~해야 한다`로 끝나는 문단 2개+ | 첫 번째만 두고 나머지는 그 문장을 문단 앞·중간으로 옮긴다 | 경고 |
| C-8 `A가 아니라 B` 대구 2번+ | 가장 좋은 1번만 남긴다 | 경고 |
| D-8 `핵심은 ~다` 분열문 | 주어-서술로 바로 쓴다 (`핵심은 검증이다` → `검증이 먼저다`) | 경고 |
| D-1 `따라서·이를 통해·요약하면` 4번+ | 1~2번만 남긴다 | 경고 |
| D-3 `다음과 같다` | 무엇을 보여 주는지 구체적으로 | 경고 |

**AI가 자주 쓰는 표현 사전** (`tools/lint_post.py`가 경고로 잡는다. 쓰지 않는다)

| 종류 | 쓰지 않을 표현 | 바꾸는 법 |
|---|---|---|
| 의의 과장 (D-2) | 시사하는 바가 크다, 주목할 만하다, 눈여겨볼 만하다, 매우 중요하다 | 지우거나 구체적인 결론으로 |
| 결말 공식 (D-6·D-9·D-10·D-12) | ~할 때다, ~로 이어진다, ~에 직결된다, ~하는 이유다, 과제도 남아 있다 | 구체적인 동사로 단언 |
